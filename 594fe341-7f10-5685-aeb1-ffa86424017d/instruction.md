# HumanInTheLoopMiddleware: review each tool call on its own, and reject an invalid answer without keeping it

I build agents with `create_agent` and `HumanInTheLoopMiddleware` from the LangChain checkout at `/app/langchain`, on the LangGraph checkout at `/app/langgraph`. Both are installed in editable mode, so a change in either takes effect at once.

Today the middleware stops once per model turn with one bundled request, and decisions are paired with calls by position. Our review screen wants one card per tool call, with a form built from a schema. Worse, an invalid answer (say an `edit` without `edited_action`) raises, but it has already been kept for the thread, so every later resume replays it and the thread never recovers.

What I need:

1. `HumanInTheLoopMiddleware(interrupt_on, interrupt_mode="per_call")`. `interrupt_mode` defaults to `"batched"`, which keeps today's behaviour exactly. Any other value raises `ValueError` reading `` `interrupt_mode` must be 'batched' or 'per_call', got 'sometimes'. `` (with the repr of the value passed). Expose the accepted values as a type alias `InterruptMode` in `langchain.agents.middleware.human_in_the_loop`.

2. With `"per_call"`, each tool call listed in `interrupt_on` pauses by itself just before it runs; unlisted calls, or calls whose `when` returns `False`, run without waiting. The pause's `value` is `{"type": "tool_approval", "tool_call_id": ..., "name": ..., "args": ..., "description": ...}`, where `description` is the configured description and a description factory receives the graph `Runtime` as in batched mode. A call whose ID is `None` raises `ValueError` containing "Tool call `<tool name>` has no ID"; an empty-string ID works.

3. The surfaced interrupt carries `response_schema`, the JSON Schema of the answers that call accepts: one `oneOf` branch per allowed decision, in `allowed_decisions` order, referencing `$defs` named `ApproveDecision`, `EditDecision`, `RejectDecision` and `RespondDecision`. In `EditDecision`, `edited_action` refers to an `EditedAction` whose `name` is a `const` equal to the tool's name and whose `args` refers to the argument schema the model sees, listed in `$defs` under the tool's name with its description. A tool allowing one decision gets that decision's plain object schema. Our review screen builds this schema directly, so provide a module-level helper `_decision_schema(allowed_decisions, tool_name, tool=None)` in that module, returning a type pydantic's `TypeAdapter` accepts.

4. I answer with `Command(resume={interrupt.id: decision})`, sometimes several pauses at once. Each answer is checked before anything about it is kept. A wrong answer raises `pydantic.ValidationError` out of `invoke` or `ainvoke` with exactly one error at the actual problem: `edit.edited_action` when missing; the tag error listing the allowed tags (such as `expected tags: 'approve', 'reject'`) for a disallowed `type`; `edited_action.name` when an edit names another tool; the argument's path when a required argument is missing. Afterwards nothing of the answer was kept and the tool did not run, so the pause can be answered again, also with `ToolRetryMiddleware` or `ToolErrorMiddleware` listed after the review middleware. For a tool whose arguments are a plain JSON Schema, or with no tool object, `args` is shown but any object is accepted.

5. `approve` runs the call as made. `edit` runs the tool with exactly the reviewer's `args`; undeclared arguments are ignored as from the model, the tool's validators and injected arguments such as `ToolRuntime` still apply, and the result keeps today's edit notice. `reject` and `respond` produce the same tool messages as in batched mode. A retried tool is not reviewed again, no tool runs twice, and the async path works.

6. I also call LangGraph's `interrupt` in my own graphs and need the same there: `interrupt(value, response_schema=...)` takes a JSON Schema `dict` or any type pydantic can validate, and the surfaced `Interrupt` carries it as `response_schema`, the dict unchanged or pydantic's JSON Schema for the type. It is a field of `Interrupt`, constructible as `Interrupt(value=..., id=..., response_schema=...)`, and present wherever an interrupt is surfaced, stored or rendered. On resume a dict schema is not enforced, while a type schema validates the answer and `interrupt` returns the validated object; an invalid answer raises `pydantic.ValidationError` and nothing of it is kept.

7. Nothing else may break: the existing behaviour of both checkouts stays the same, and callers of `interrupt` that pass no schema see no difference.

How I'd like it done: a focused change in the style of the surrounding code in each checkout. An answer should be checked in one place, and resuming should follow the same rule whether the answer arrives through the middleware or through my own graphs. Bad answers should fail loudly rather than be swallowed or patched over, the behaviour should hold for any tool and any schema rather than just the cases above, and any docstring or comment you touch should describe what the code does.
